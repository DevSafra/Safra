# Copy and languages

**The rule: no user-facing text is written inside code.** Every word a person reads comes from a
catalogue in `@safra/i18n`, keyed, in each locale that surface serves.

Bashar set this on 2026-08-04, and the reason is narrow and practical: _adding a language has to
be a task somebody can finish_. A sentence in a `.tsx` file is invisible to that task, and the way
you find out it was there is a German customer reading Arabic.

---

## 1. Where copy lives

| Surface             | Catalogue                        | Locales                  | Read by                       |
| ------------------- | -------------------------------- | ------------------------ | ----------------------------- |
| Customer site       | `messages/web/{ar,en,de}.json`   | all three, **complete**  | next-intl (`useTranslations`) |
| Staff console       | `messages/admin/ar.ts`           | Arabic only, by decision | `t` from `@/lib/strings`      |
| Transactional email | `messages/email/{ar,en,de}.ts`   | all three, **complete**  | `emailMessages(locale)`       |
| Server errors       | `messages/errors/{ar,en,de}.ts`  | all three, **complete**  | `errorMessage(code, locale)`  |
| Stored content      | `messages/content/{ar,en,de}.ts` | all three, **complete**  | `contentMessages()`           |

The locale list itself is in `packages/i18n/src/locales.ts`. It is the single answer to "how many
languages does SAFRA speak" — the customer app's next-intl routing derives from it rather than
declaring its own.

### Why the customer catalogues are JSON and the rest TypeScript

next-intl reads JSON natively and resolves ICU, which customer copy genuinely needs — plurals,
dates, currency — and JSON is what a translation service accepts. The other surfaces need
`as const` instead, because that is what lets `fill()` read placeholder names out of the literal
types and check them at compile time.

---

## 2. Interpolation

Placeholders, never template literals:

In the catalogue:

```ts
inviteSent: 'أُرسلت الدعوة إلى {email}.',
```

At the call site:

```ts
fill(t.sections.staff.inviteSent, { email });
```

A JS template literal freezes word order where it is written, and word order is the first casualty
of translation — German puts the participle last, Arabic puts the verb first. A translator handed
`` (email) => `أُرسلت الدعوة إلى ${email}.` `` has to edit code to move a value.

`fill()` reads the placeholder names out of the template's literal type, so a missing or misspelt
value **does not compile**:

```ts
fill(t.sections.staff.inviteSent, { emial: email });
//                                  ^^^^^ 'emial' does not exist in type
//                                        Values<"أُرسلت الدعوة إلى {email}.">
```

> This checking silently did nothing at first. TypeScript treated the _values_ as inference
> candidates for the template type, so a `string`-typed value widened it to `string` and the
> permissive branch accepted anything. `NoInfer<S>` is what fixes it — see the note in `fill.ts`.
> It only ever appeared to work when tested with literal values.

### Plurals

Do not build them with a conditional. `{n} night{n === 1 ? '' : 's'}` is a rule about English
grammar written into a component; Arabic has six plural forms and does not use any of them the way
that expression assumes. Phrase the sentence so the count is a value (`'{nights} ليلة'`), or use
ICU on the customer side where next-intl resolves it per locale.

## 3. Server errors are codes, not sentences

The API answers `{ statusCode, code, message }`:

```ts
throw notFound(ERROR.BOOKING_NOT_FOUND);
// → { statusCode: 404, code: 'booking.not_found', message: 'Booking not found.' }
```

- **`code`** is the contract. Stable, translatable. Clients resolve it with `errorMessage(code, locale)`.
- **`message`** is English, for logs and for clients that have not been taught the codes.
  **Never display it** — it is not in the reader's language.

Helpers are in `apps/api/src/common/errors/app-error.ts`, one per status. The status stays at the
call site so a code→status table cannot silently move an existing response.

Zod schemas in `@safra/contracts` set their message to a code too, so `ZodValidationPipe` emits
`errors: [{ field, code, message }]` and a form resolves the code next to the input.

**Adding a code** means an entry in `packages/contracts/src/error-codes.ts` and a translation in
all three error catalogues. The `errors-complete` test fails until both exist, so a raw
`booking.not_found` cannot reach a user.

Renaming a code is a breaking change for every client. Add a new one and leave the old.

## 4. What is NOT copy

These are the documented exceptions. They exist because a rule that over-reports gets switched
off, and one that is switched off permits everything.

| Thing                                    | Where it goes                      | Why                                                                                                               |
| ---------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `۞` `☾` `✦` `☀`                          | `@safra/ui/ornaments`              | Glyphs, not words. No translation exists.                                                                         |
| `brand.name`, `brand.latin`              | catalogue, untranslated on purpose | The two halves of the wordmark. Translating it would rename the company.                                          |
| Language labels (`Deutsch`)              | `LOCALE_LABELS`                    | A German speaker scans for "Deutsch", not "الألمانية".                                                            |
| Enum values, setting keys, template keys | schema / code                      | A machine reads them. Translating one breaks what identifies it.                                                  |
| Reference prefixes (`BKG-`)              | code                               | Part of an identifier customers quote to support.                                                                 |
| Weekday and month names                  | `Intl.DateTimeFormat`              | The platform already has them correct for every locale. Verified to match the design for `ar`.                    |
| Currency **codes** (`SYP`)               | code                               | The **symbol** (`ل.س`) is copy and is in the catalogue; the code is not.                                          |
| Test fixtures                            | tests                              | Data about what a server returned, not copy shown to anyone.                                                      |
| Internal `new Error(...)`                | code                               | Never reaches a browser. Nest answers a generic 500 and the text goes to the log, which is where rule 1 wants it. |

## 5. Enforcement

**Lint** — `tools/eslint-rules/no-hardcoded-text.mjs`, wired into `pnpm lint`, so CI blocks it.
It flags JSX text, user-facing JSX attributes (`placeholder`, `title`, `alt`, `aria-label`,
`label`) and client-facing exception messages. It has its own tests, because a rule that
over-reports gets deleted.

It **cannot** catch a prose string passed to a function it does not know about —
`setError('Try again')`. Covering that would mean flagging every string literal in the repo. For a
broader sweep:

```bash
# Arabic literals outside the catalogues
grep -rnP '[\x{0600}-\x{06FF}]' apps/*/src packages/*/src --include='*.ts' --include='*.tsx' \
  | grep -v packages/i18n/src/messages
```

**Tests** — `packages/i18n/src/completeness.test.ts` asserts, for every catalogue:

- every locale has exactly the Arabic key set, in both directions;
- no value is empty;
- no non-Arabic locale still contains Arabic text (an untranslated key copied and left);
- placeholders agree across locales — a German translation using `{days}` where Arabic uses
  `{maxDays}` renders a literal `{days}` to a customer, and nothing else would catch it;
- every email body keeps its `{url}`;
- every error code is translated in all three, with no orphaned entries;
- **no catalogue value contains an Arabic-Indic digit** — see §8.

## 6. Adding a language

1. Add it to `LOCALES` in `packages/i18n/src/locales.ts`, with a direction and an endonym label.
2. `pnpm --filter @safra/i18n typecheck` — the email, error and content registries are full
   `Record<Locale, …>`, so the compiler now lists what is missing.
3. Write `messages/{email,errors,content}/<locale>.ts` and `messages/web/<locale>.json`.
4. `pnpm test` — the completeness tests enumerate every remaining gap by key.
5. The customer app needs nothing further: routing, `generateStaticParams` and the language
   switcher all derive from `LOCALES`.

**The staff console is a separate decision.** It is Arabic-only (Bashar, 2026-08-03) and nothing
fabricates an English or German console — 800 unreviewed strings would look like progress and read
as machine output to the people who run the business on it. To add one: write
`messages/admin/<locale>.ts` with `satisfies AdminMessages`, register it in `admin.ts`, and change
the one line in `apps/admin/src/lib/strings.ts` that binds `t`. Placeholder checking then hands
over from the compiler to the completeness tests, which is why they exist.

## 7. The redaction mask — closed 2026-08-14

This section recorded a limitation: `redactionMask` was baked into stored message text at write
time, so it could not follow the reader — a German customer reading a redacted Arabic thread saw
`⟨محجوب⟩`. **That is fixed** (register item `O-i18n-2`). A message now stores `REDACTION_TOKEN`,
a language-neutral `⟦…⟧`, and `renderRedactions(body, locale)` resolves it for whoever is reading.

Three things about it that are easy to undo by accident:

- **The token is PUNCTUATION deliberately.** It matches none of the redaction patterns, which is
  what keeps `redactContactDetails` idempotent, and it is also the fallback rendering — it says
  "something is missing" in no language rather than the wrong one.
- **Stripping forged markers belongs at the boundary, not inside the primitive.** Doing it inside
  `redactContactDetails` un-redacts a message on a second pass, because by then the marker in the
  text is our own. It lives in `redactIncomingMessage()`, which services call exactly once.
- **`LEGACY_MASKS` in `content.ts` is permanent, not transitional.** `messages` is append-only —
  `deny_mutation` raises on UPDATE — so old bodies cannot be migrated, and should not be: they are
  dispute evidence.

## 8. Numbers are written 0-9

**Standing instruction from Bashar, 2026-08-17: every number and every price a person reads is in
Western digits, in every surface and every locale.** Arabic copy, Western numerals — which is what
the design handoff uses throughout ("الأربعاء 23 تموز 2026", "عمولة الشريك 7٪").

There are two ways a digit reaches a screen, and only one of them was ever protected:

- **From data, through a formatter.** Safe, and has been all along. `ARABIC_WESTERN_DIGITS`
  (`ar-SY-u-nu-latn-ca-gregory`) pins the console and لوحة الشريك; the customer app passes
  `numberingSystem: 'latn'` explicitly. An `ar` locale left to itself picks Arabic-Indic, so these
  are load-bearing — do not "simplify" one back to a bare `'ar'`.
- **Typed into a sentence.** Unprotected until 2026-08-17. «الغرامة ١٠$» was written as text in the
  partner catalogue and rendered `$١٠`on a dashboard where every other figure read`$10`. Eighteen
  strings across five catalogues had it, and no formatter, type or test could see any of them.

`completeness.test.ts` now sweeps every catalogue in every locale and fails on any Arabic-Indic
(`٠-٩`) or Extended Arabic-Indic (`۰-۹`) digit in a value.

**A number spelled out is a word, not a numeral.** «ستة أرقام» and «ساعتين» are copy and stay as
they are — the test looks only at digits.

## 9. Direction: a field a person types into follows the page

**Standing instruction from Bashar, 2026-08-19**, applying to every input, textarea and select in
every app, present and future. On an Arabic screen that means RTL — the label sits on the right, so
the caret and the value must start on the right too.

`dir="ltr"` sets the direction **and** moves the element's start edge. That is what put «رقم الوحدة»
on the right of its own field and `101` on the far left of it.

It reads as a contradiction of "keep Latin runs readable", and it is not — the two problems have
different answers, and using the DISPLAY answer on a FIELD is the mistake:

| Situation                                                  | Answer                                                       | Why                                                                                                                                         |
| ---------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Somebody **types** into it                                 | No `dir`, or `dir="rtl"` where a component requires the prop | `A-12`, `+963…` and an email are left-to-right RUNS, and the bidi algorithm lays a run out correctly inside an RTL field without being told |
| **Displaying** a Latin value on a line of Arabic           | Isolate the VALUE only — `<Ltr>`, `ltrIsolate()`             | Wrapping the label too puts it inside the LTR run: «وحدة A-12» renders «A-12 وحدة», colliding with whatever precedes it                     |
| A whole field that **must** read left-to-right (IBAN, URL) | `field-ltr`                                                  | It sets the direction and takes the ALIGNMENT from the document. `dir="ltr"` alone is always wrong on a field                               |

A `Field` component that makes `dir` REQUIRED is doing the right thing: it forces the choice to be
made rather than inherited by accident.

**No exceptions remain.** Four staff-console inputs predated the rule — the booking-reference
lookup, the dispute-form amount, the staff invite email and a setting value — and were corrected on
2026-08-19. The `dir="ltr"` still on spans, cells and paragraphs in that app is the DISPLAY case and
is correct.
